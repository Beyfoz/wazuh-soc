# Лаба 4. Учётные записи Windows: создание, администратор, удаление

**Дата:** 05.11.2026 · **Агент:** Win10-Host (001) · **Канал:** Security (EventChannel)

## Цель

Увидеть в журнале безопасности Windows события входа и управления учётными записями и связать их с техниками MITRE.

## Что сделал

1. Выполнил несколько неудачных входов под несуществующим пользователем.
2. Создал локального пользователя `labtest`.
3. Добавил `labtest` в локальную группу «Администраторы».
4. Удалил `labtest`.

## Разбор

| Вопрос | Ответ |
|---|---|
| Что произошло | На хосте создан новый локальный пользователь `labtest`, добавлен в группу администраторов и затем удалён. |
| Кто выполнил действие | `data.win.eventdata.subjectUserName` = пользователь хоста, действие выполнено из его сессии. |
| Над кем | `data.win.eventdata.targetUserName` = `labtest` (создание, удаление) и `Администраторы` / домен `Builtin` (изменение группы). |
| Где смотреть | Поля `data.win.system.eventID`, `data.win.system.message`, `data.win.eventdata.*`. |
| MITRE | Wazuh указал: 60109 → T1098 Account Manipulation; 60154 → T1484 (Domain Policy Modification); 60111 → T1098, T1531 Account Access Removal. По смыслу создание локальной учётки это T1136.001 (Create Account: Local Account), а добавление в Administrators ближе к T1098, чем к T1484 (она про доменные политики): это моё уточнение. |
| Оценка | Безвредный тест. |
| Серьёзность | Высокая в реальной сети: появление нового локального администратора означает возможную полную компрометацию и закрепление (level 12). |

## Что бы делал в реальном инциденте

Изолировал бы хост от сети, проверил по Sysmon и Security, кто и с какого процесса создал учётную запись, и как атакующий получил права. Проверил бы хост на следы закрепления (автозагрузка, службы, задачи планировщика), сменил учётные данные.

## Как предотвратить

Ограничить права пользователей на локальное администрирование и запуск привилегированного PowerShell, включить строгий аудит командной строки, настроить UAC, отключить устаревшие протоколы NTLM и SMBv1, ограничить сетевой доступ к административным ресурсам.

## Наблюдение: расхождение времени

В алертах время менеджера Wazuh (`timestamp`) раньше времени события Windows (`data.win.system.systemTime`), что невозможно при нормальной работе: алерт не может появиться раньше события.

| Событие | `systemTime` (Windows, UTC) | `timestamp` (менеджер, UTC) | Расхождение |
|---|---|---|---|
| 4720 создание | 12:00:19 | 11:37:52 | 22 мин 28 с |
| 4732 администраторы | 12:03:54 | 11:39:49 | 24 мин 05 с |
| 4726 удаление | 12:48:58 | 12:03:17 | 45 мин 41 с |

Расхождение растёт, поэтому, вероятно, отстаёт часы ВМ с менеджером (на сервере периодически были зависания ядра, см. [docs/setup.md](../../docs/setup.md)). В результате время в Dashboard сдвинуто относительно реальности, хотя порядок событий сохраняется. В реальном SOC такие расхождения ломают хронологию, поэтому первым делом проверяют источники времени.
